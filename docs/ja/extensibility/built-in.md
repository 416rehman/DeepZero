## 組み込みプロセッサ

名前だけで参照します。`deepzero list-processors` を実行すると、実装クラスとあわせて一覧できます。

| 識別子 | タイプ | 機能 |
| ------------- | ---- | ------------- |
| `file_discovery` | Ingest | ファイルシステムの再帰的な走査と暗号化ハッシュ。 |
| `metadata_filter` | Map | `require:` によるフィールドの一致判定、`min_<field>` / `max_<field>` キーによる数値のしきい値、`dedup_field` による重複排除。フィールドは上流のすべてのステージのデータをマージしたものから読み取られます。 |
| `hash_exclude` | Map | YAML に直接書いたリストまたはフラットファイルを使用した暗号化ハッシュによる除外、`dedup` による実行中の重複排除、そして `hash_field` によるハッシュの読み取り元フィールドの指定（未設定なら `sha256`）。 |
| `generic_llm` | Map | Jinja2 テンプレートのレンダリング、LLM の呼び出し、および応答の解析。 |
| `generic_command` | Map | コンテキスト変数の置換を伴う任意のシェルコマンドの実行。 |
| `top_k` | Reduce | 数値スカラー値に基づいてサンプルセットを切り捨てます。 |
| `sort` | Reduce | データセットを縮小せずにサンプルを決定論的に並べ替えます。 |

`min_<field>` のしきい値は、上流のどのステージも記録していないフィールドをゼロとして読み取り、そのサンプルをフィルタリングします。フィールドが本当に存在しない場合はこれが正しい答えですが、名前が変わっただけのフィールドに対しては誤った答えになります。あるステージが数秒でコーパス全体をフィルタリングしてしまうときは、上流が実際に提供している名前と突き合わせて確認する価値があります。

## 同梱の外部プロセッサ

これらは `processors/` に置かれ、パスで参照されます。つまり特権的な組み込みではなく、通常の外部プロセッサとして読み込まれます。[同梱パイプライン]({{ '/ja/reference/included-pipeline.html' | relative_url }})が使用しているのはこれらです。`ghidra_decompile`、`git_ingest`、`loldrivers_filter` は受け付けるキーを `Config` データクラスとして宣言しているため、その一覧はソースそのものであり、パイプラインで綴りを間違えたキーは無視されずに報告されます。`pe_ingest` と `semgrep_scanner` は生の設定辞書を読むため、そこで綴りを間違えたキーは読まれもしなければ報告もされません。いずれもソースの隣に README を備えており、何を出力するか、そして読み手が驚くであろう挙動を説明しています。

| パス | タイプ | 機能 |
| ---- | ---- | ------------- |
| `pe_ingest/pe_ingest.py` | Ingest | PE ファイルを検出し、ヘッダーを解析して、ドライバーのメタデータを抽出します。 |
| `git_ingest/git_ingest.py` | Ingest | チェックアウトのディレクトリ、または URL のマニフェストから、git リポジトリをサンプルに変換します。 |
| `loldrivers_filter/loldrivers_filter.py` | Map | SHA-256 が loldrivers.io データベースの既知のエントリと一致するサンプルを除外します。 |
| `ghidra_decompile/ghidra_decompile.py` | Map | ポストスクリプトを設定できる Ghidra ヘッドレスデコンパイル。 |
| `semgrep_scanner/semgrep_scanner.py` | BulkMap | アクティブなサンプル全体に対する semgrep の一括スキャン。 |

### `git_ingest`

1 つのサンプルが 1 つのリポジトリであり、その `source_path` はチェックアウトのルートです。ソースコードのスキャナーに指し示したいのはまさにこの場所です。CLI のターゲットは常に実在するパスなので、どちらの入力形式でも再開とコーパスのスコープはそのまま機能します。ディレクトリはチェックアウトの入れ物として読まれ、何も取得されません。ファイルはマニフェストとして読まれ、各エントリがクローンされます。

`sample_id` はパスではなくリポジトリの同一性から導出されます。そのため、マニフェスト経由で到達したリポジトリとディレクトリ経由で到達したリポジトリは同じサンプルになり、再実行しても結果が引き継がれます。

### `semgrep_scanner`

| フィールド | デフォルト | 意味 |
|-------|---------|---------|
| `rules_dir` | なし。必須 | 読み込む semgrep ルールのディレクトリ。 |
| `target_dir` | `decompiled` | スキャンするサンプル自身のワークディレクトリ内のサブディレクトリ。`""` に設定すると、代わりにサンプル自身のパスがスキャンされます。 |
| `extensions` | `.c`、`.h`、`.cpp`、`.py` | semgrep に渡すファイル。先頭のドットがなければ補われ、1 件だけのリストは文字列 1 つでも受け付けられます。 |
| `batch_size` | `200` | semgrep 1 回の呼び出しあたりのサンプル数。`0` 以下にすると、そのステージ全体を 1 回の実行にまとめます。 |
| `timeout` | `300` | 1 バッチの semgrep プロセスに許される秒数。 |
| `min_findings` | `0` | 検出結果がこの件数に満たないサンプルを除外します。`0` なら何も除外しません。 |

1 つのスキャナーで同梱の両パイプラインをまかなえるのは、`target_dir` と `extensions` があるからです。デフォルトは、先にデコンパイルして各サンプルの隣に C を書き出すパイプラインに向いています。サンプルがすでにソースコードであるパイプライン、たとえばリポジトリのチェックアウトを扱う場合は、`target_dir: ""` を設定し、`extensions` を実際に取り込んだものに合わせて広げます。

`rules_dir` は、まず作業ディレクトリを基準に、次にパイプラインディレクトリを基準に解決されます。`validate()` とスキャン本体は同じ手順で解決します。かつてこの 2 つが異なる解決をしていたために、検証は通るのにスキャンはルールを 1 つも読み込まないまま走る、ということが起きたからです。ステージの実行時に `rules_dir` が存在しない場合は、何も読み込まずにスキャンしてきれいなコーパスを報告するのではなく、そのステージのすべてのサンプルを失敗させます。

#### すでにある findings.json は再スキャンされずに採用される

これが意外な点です。何かをスキャンする前に、このプロセッサは各サンプル自身のディレクトリにある `findings.json` を探します。それが存在し、エンジンがキャッシュされた結果を今も有効だと報告し、そのファイルが解析できる場合、その検出結果が結果として採用され、そのサンプルは `findings_cached: true` とともに記録され、semgrep はそのサンプルについて何も尋ねられません。有効かどうかを判断するのはこのプロセッサの仕事ではありません。エンジンは、このステージの現在のフィンガープリントと、前回の結果が記録されたときのフィンガープリントとを突き合わせます。そのファイルが今も効力を持つルールと設定を記述しているかどうかを知りうるのは、エンジンだけだからです。ファイルが読めない場合は、代わりに再スキャンされます。

中断された実行が、すでに終えたバッチを繰り返さずに済むのはこれによります。ルールを書き換えれば、それだけでキャッシュは無効になります。`rules_dir` はディレクトリを指す設定値であり、ルールファイルそのものがフィンガープリントに畳み込まれるため、別のフィンガープリントで記録された結果は採用されずに古いものとして扱われます。フィンガープリントからは見えないもののために再スキャンを強いる手段は、引き続き `deepzero run --redo <stage>` です。これが機能するのは、`findings.json` が、除外の経路も含めてそれを書き出すすべての経路でアーティファクトとして記録されているからです。だから `--redo` はそのファイルを見つけて削除できます。フィンガープリントが存在しなかった頃に記録された結果は空のダイジェストを持ちますが、それらはそのまま信頼されます。この機能より前に作られたという理由でコーパスを捨てるほうが、より悪い判断だからです。

採用された結果が持つのは `finding_count` と `findings_cached` だけです。`files_submitted` と `files_scanned` は semgrep の実行そのものから来るため、今回スキャンされなかったサンプルにはどちらもありません。

#### バッチ処理と、知っておく価値のある失敗

サンプルは 1 回の実行にまとめるのではなくバッチ単位でスキャンされます。タイムアウトしたり読めない結果が返ってきたりしたバッチのコストが、すでに終えた作業ごとコーパス全体を捨てるのではなく、そのバッチ分のサンプルだけで済むようにするためです。`timeout` を超えたバッチは、その中のすべてのサンプルを失敗として記録します。

`extensions` とルールは一致していなければなりません。拡張子が列挙されていないファイルは、どれだけ多くのルールが一致したはずでも semgrep に渡されず、しかもその失敗は表に出ません。スキャンは検出結果ゼロを報告し、それはきれいなツリーと見分けがつきません。ソースコード監査パイプラインが `finding_count` と並べて `files_scanned` を記録しているのはこのためです。

さらに 2 つの結果は、きれいと報告されるのではなく拒否されます。どちらも外から見るときれいなコーパスとまったく同じに見えるからです。semgrep が読み込みエラーを返しながら結果を 1 つも出さなかった場合と、semgrep が提出されたファイルを 1 つも読まなかったと報告した場合です。どちらもそのバッチを失敗させ、その旨を伝えます。

`target_dir` がディスク上にないサンプルは、バッチが組まれる前に、それ単独で失敗します。そのメッセージは、そのディレクトリを生み出すステージがこのステージより先に走っているかを問いかけます。たいていはそれが答えです。

`min_findings` はこのステージでサンプルを失敗させるのではなく除外するため、理由が記録され、`findings.json` も付いたまま実行を去ります。同梱の 2 つのパイプラインはどちらも `min_findings: 1` を設定しています。これが、何も指摘されなかったサンプルが下流でモデル呼び出しを消費するのを止めています。
