## コマンドラインインターフェース

`deepzero` CLI は、パイプラインを実行および管理するための主要な相互作用ポイントです。

```bash
# 標準実行
deepzero run ./targets -p pipelines/loldrivers/pipeline.yaml

# 長い実行に踏み切る前に、LLM バックエンドがサインイン済みか確認する
deepzero run ./targets -p pipelines/source_audit/pipeline.yaml --preflight

# 状態をクリアして実行 (クリーンラン)
deepzero run ./targets -p pipelines/loldrivers/pipeline.yaml --clean

# 閲覧可能な HTML レポートを構築して開く
deepzero report -p loldrivers --open

# 実行ステータスの確認
deepzero status -p loldrivers

# 対話型分析 REPL の起動
deepzero interactive -w work/loldrivers

# Starlette REST API を起動
deepzero serve -w work/loldrivers --port 8420

# カスタムパイプラインの雛形作成
deepzero init my_custom_pipeline

# 実行せずにスキーマを検証
deepzero validate loldrivers

# システムレジストリのリスト
deepzero list-processors
```

`deepzero --version` はインストール済みのバージョンを表示します。`--help` はコマンドグループでも個々のコマンドでも使えます。

### 主要なコマンド

| コマンド | 説明 |
| ------- | ----------- |
| `run` | ターゲットに対してパイプラインを実行します。状態が存在する場合は自動的に再開します。 |
| `report` | 実行結果から閲覧可能な HTML レポートを構築します。実行中に走らせても安全です。 |
| `status` | パイプライン実行の現在のステータス、判定、ステージメトリクスを表示します。 |
| `validate` | パイプラインのスキーマ、プロセッサのインポート、プロンプトをドライランで検証します。 |
| `list-processors` | 組み込みおよび動的に登録されたすべてのプロセッサタイプを一覧表示します。 |
| `init` | 定型の `pipeline.yaml` を備えた新しいパイプラインディレクトリを作成します。 |
| `interactive` | パイプラインの結果について LLM と対話しながら分析する REPL。 |
| `serve` | パイプラインの状態を外部へ公開する REST API サーバーを起動します。 |

### `run`

```bash
deepzero run <TARGET> -p <pipeline> [options]
```

| フラグ | デフォルト | 説明 |
|------|---------|-------------|
| `TARGET` | 必須 | 位置引数。解析コーパスへのパス。実在している必要があり、ファイルとディレクトリのどちらでも、パイプラインのインジェストステージが受け付ける方を指定します。 |
| `-p, --pipeline` | 必須 | パイプライン名、ディレクトリ、または個別の YAML ファイルパス。 |
| `-m, --model` | パイプラインの `model` | この実行だけ LLM モデルを上書きします。例: `openai/gpt-4o`。 |
| `-w, --work-dir` | パイプラインの `work_dir` 設定 | 実行ディレクトリを作るルートを置き換えます。 |
| `--clean` | off | 以前の実行データを完全に削除し、最初からやり直します。 |
| `--preflight` | off | 実行前に LLM バックエンドが認証済みかを確認します。ごく小さな呼び出しを 1 回行います。 |
| `--redo` | なし | 名指ししたステージとそれ以降をすべて再実行します。それより前の作業は保持し、それらのステージが記録した出力は削除します。繰り返し指定できます。 |
| `--retry-timeouts` | off | 時間切れになったサンプルを再度試みます。それ以外の結果はすべて保持します。 |
| `--timeout-multiplier` | `2.0` | 時間切れになったステージを再試行する際に、どれだけ長く猶予を与えるか。 |
| `-v, --verbose` | off | 詳細ログ。DeepZero 自身のコードのトレースバックも含みます。 |

状態のない実行は最初から始まり、状態のある実行は再開します。どの実行を引き継いだのかはヘッダーに表示されます。実行の間に `--model` を変更することは許可されており、その事実は記録されます。実行状態は実際に呼び出されるモデル名に更新されるため、`status` やレポートが、もう使われていないモデルについて説明することはありません。

`--clean` は以前のディレクトリを脇に退避させてから、バックグラウンドで削除します。そのため、数十万ファイルのコーパスであっても、削除が終わるまでコマンドが占有され続けることはありません。

#### 実行の状態が置かれる場所

ワークディレクトリはコーパスごとにスコープされます。

```text
<work_dir setting>/<pipeline name>/<corpus key>/
```

コーパスキーはターゲットパスから導出されます。ベース名に、解決された絶対パスの短いダイジェストを付け加えたものです。したがって、同じパイプラインを通した 2 つのコーパスがサンプルストア、マニフェスト、レポートを共有することは決してなく、それぞれ独立して再開します。同じパスからは常に同じキーが得られるため、再実行すれば元のディレクトリに戻ります。

`run` の `-w, --work-dir` が置き換えるのは最初のセグメントだけです。パイプラインとコーパスのセグメントは引き続き付加されます。2 つの実行を切り分けているのがそれらだからです。

#### 実行が進みながら書き出すレポート

実行は `<work dir>/report` に HTML レポートを書き出し、最初のステージが始まる前にその URL を表示します。レポートはタイマーではなく結果が届いたタイミングで再構築され、その頻度は 15 秒に 1 回までです。処理の速いステージが実行時間を HTML の書き出しに費やしてしまわないようにするためです。実行が中断されたときも完了したときも、停止時にもう一度書き出されるため、ディスク上にあるものは常に最終状態です。

#### 長い実行の前に LLM を確認する

`--preflight` はバックエンドに準備ができているかを尋ね、できていなければ開始を拒否します。これがあるのは、そうでなければ数時間経ってから、しかも手前の高価なステージがすでに走り終えたあとの、最初の評価ステージで気づくことになるからです。

この確認が何をするかはバックエンドによって異なります。認証済みであることの意味がバックエンドごとに違うためです。`claude-code` のようなエージェント CLI のバックエンドは最小のプロンプトを 1 回送ります。そのバイナリがサインイン済みかどうかは、DeepZero がディスクから読み取れるものではないからです。API キーのバックエンドは、検証時にすでに済ませたキーの確認から答えるため、何も消費しません。

レート制限やネットワークエラーは認証の失敗として扱われず、実行を止めません。この確認が常時ではなくオプトインなのは、そのプロンプト 1 回が、どれほど小さくとも実際の使用量だからです。

この確認が走るのは、パイプラインがモデルを設定している場合だけです。LLM ステージのないパイプラインには確認すべきものがありません。

#### 時間切れになったものを再試行する

`timeout` に達したステージは、そのサンプルを失敗ではなく時間切れとして記録します。これはサンプルについての言明ではなく、予算についての言明です。時間切れになるのは最も大きなものであり、たいていのコーパスではそれこそが見るに値するものです。それらを本物のエラーと一緒に綴じてしまうと、実行はひそかにそれらから目を逸らす方向に偏ります。

予算が縛るのはステージが待つ長さであって、作業にかかる長さではありません。プロセッサのスレッドは終了させられるのではなく放置されるため、そのスレッドが起動した外部プロセスは、ステージが先へ進んだあともまだ動いています。[`timeout`]({{ '/ja/reference/pipeline-yaml.html' | relative_url }}) を参照してください。

再開した実行は、時間切れになったものを自動では再試行しません。短すぎた予算が今も短いままだからです。必要なら明示的に指示します。

```bash
deepzero run <target> -p <pipeline> --retry-timeouts
```

これは時間切れになったステージだけを忘れ、そこに `--timeout-multiplier`（デフォルトは 2 倍）の猶予を与えます。実行が生み出した他の結果はすべて保持されるため、再試行にかかるのはそれらのステージが必要とする時間だけです。タイムアウトを宣言していないステージには手を触れません。レポートはそれらを別立てで分類し、超過した予算をそれぞれ表示します。

#### 1 つのステージだけを再実行する

プロンプト、ルールセット、スキャナーの設定を書き換えると、そのステージの結果は無効になりますが、それより前のものは無効になりません。同じコーパスに問いを立て直すためだけにもう一度デコンパイルすれば、理由もなく数時間かかります。そこで、ステージを名指しします。

```bash
deepzero run <target> -p <pipeline> --redo assess
```

各サンプルはそのステージと、それ以降のすべてのステージを忘れ、それより前はすべて保持します。後続のステージも一緒に落ちるのは、それらがこれから変わる出力を消費していたからです。もう存在しない検出結果から書かれた評価が残れば、1 つのサンプルが 2 つの異なる実行を同時に記述することになります。古くなったステージが除外したサンプルは実行に復帰するため、絞り込んだルールセットはそれについて違う判定に達することができます。

それらのステージが記録した出力も、状態と一緒に消えます。いくつかのプロセッサはディスク上にある自分の出力ファイルをキャッシュとして扱い、作業をやり直す代わりにそれを採用します。そのため状態だけを忘れさせると、そのステージは古いファイルを採用し直して新しい結果として記録することになり、やり直さないよりも悪い状態になります。そこで `--redo` は、落としたステージが記録していたアーティファクトをそれぞれ削除し、何ファイル削除したかを表示します。サンプル自身のディレクトリの外に記録されたアーティファクトには手を触れません。この実行が削除してよいものではないからです。

`--redo` は繰り返し指定でき、名指しされた中で最も手前のステージから始まります。存在しないステージ名は、何もすることがないものとして扱われるのではなく、そのパイプラインの実際のステージ名を列挙したうえで拒否されます。名指しされたどのステージにもサンプルが到達していなかった場合は、その旨を表示して何も変更しません。

### `report`

```bash
deepzero report -p <pipeline> [--open]
deepzero report -w work/loldrivers/drivers-1a2b3c4d
```

| フラグ | デフォルト | 説明 |
|------|---------|-------------|
| `-p, --pipeline` | なし | パイプライン名またはパス。そのパイプラインの最新のコーパスに解決されます。 |
| `-w, --work-dir` | なし | 実行ディレクトリ、またはパイプラインのルート。後者の場合は最新のコーパスが読まれ、その名前が示されます。`--pipeline` より優先されます。 |
| `-o, --out` | `<work_dir>/report` | レポートの書き出し先。 |
| `--open` | off | 完成したレポートをブラウザで開きます。 |
| `-v, --verbose` | off | 詳細ログ。 |

`--pipeline` と `--work-dir` のいずれか一方が必要です。

レポートは実行状態だけから導出されるため、実行ディレクトリにない情報は持ちません。レポートのディレクトリを削除してコマンドを実行し直せば、元どおりになります。実行中に構築しても安全です。状態ファイルを読むだけで、ランナーが依存するものは何も書かないため、構築した瞬間の実行内容を記述します。

書き出されるもの：

| ファイル | 内容 |
|------|----------|
| `index.html` | サマリーと、サイズに上限のある順位付きリスト |
| `items/<id>.html` | 読む価値のあるサンプルごとに 1 ページ。そのサンプルのアーティファクトへリンクします |
| `inventory.csv` | すべてのサンプルを 1 行ずつ。表計算ソフト向け |
| `findings.jsonl` | すべての検出結果を 1 行 1 JSON オブジェクトで |
| `report.json` | 機械向けのサマリーの合計と、それらを呼ぶための語彙 |

サンプルが専用のページを持つのは、そこに読むべきものがある場合です。検出結果、評価、エラー、あるいは時間切れになったステージがある場合です。それ以外も CSV には残り、一覧が打ち切られたときはその旨と残りの在り処をインデックスが示します。

パイプライン名で解決すると最新のコーパスが選ばれます。そのパイプラインが複数のコーパスを見てきた場合は、その旨と他のコーパス名が示されます。最も新しい実行が、いつも尋ねられている実行だとは限らず、別のコーパスについて黙って答えてしまうことこそ避けるべき失敗だからです。1 つを厳密に指定するには `--work-dir` を渡します。

そのパイプラインがサンプル、結果、そして向けられた対象を何と呼ぶかは、パイプラインの `report:` ブロックから来ます。このブロックがあるのは実行ディレクトリではなくパイプライン定義の側ですが、`--work-dir` でもそれは手に入ります。実行はどのパイプラインが自分を書いたかを記録しているため、ブロックはその名前から復元されます。ただし、実行は自分を作ったパイプラインより長く残ることがあります。そのパイプラインがもう読み込めない場合、レポートは構築を拒否するのではなくデフォルトの語彙に戻ります。[report ブロック]({{ '/ja/reference/pipeline-yaml.html' | relative_url }})を参照してください。

### `status`

```bash
deepzero status -p loldrivers
```

| フラグ | デフォルト | 説明 |
|------|---------|-------------|
| `-p, --pipeline` | なし | パイプライン名またはパス。そのパイプラインの最新のコーパスに解決されます。 |
| `-w, --work-dir` | なし | 実行ディレクトリ、またはパイプラインのルート。後者の場合は最新のコーパスが読まれ、その名前が示されます。`--pipeline` より優先されます。 |
| `-v, --verbose` | off | 詳細ログ。 |

いずれか一方が必要です。実行 ID、ターゲット、モデル、タイムスタンプ、完了・フィルタ済み・失敗・時間切れの件数をステージごとに並べた表、そしてサンプル判定の合計を表示します。時間切れが独立した列を持っているのは、すべてが時間切れになったステージが、誰も到達しなかったステージのように読まれないようにするためです。それは実際に起きたことの正反対です。

### `validate`

```bash
deepzero validate <PIPELINE_REF>
```

パイプラインを読み込み、すべてのプロセッサを解決し、各プロセッサ自身の `validate()` を実行し、さらにすべてのプロンプトを、それより前のステージが実際に生み出す値と突き合わせて検査します。フラグはありません。長い実行の前に走らせてください。バイナリの欠落、読めないルールセット、どのステージも記録しない名前を指すプロンプトを見つける場所としては、ここが最も安上がりです。

エラーを報告したときは終了コード 1 を、そうでなければ 0 を返すため、コミットの門番として使えます。モデルを設定していないパイプラインのような警告は表示されますが、コマンドを失敗させることはありません。警告が表しているのは、起動できないパイプラインではなく、起動はするパイプラインだからです。

### `list-processors`

登録済みのすべてのプロセッサを、そのタイプと実装クラスとともに表示します。フラグはありません。一覧に出るのは組み込みだけです。外部プロセッサは読み込み時にパスから解決されるもので、名前で登録されてはいません。

### `init`

```bash
deepzero init <NAME>
```

作業ディレクトリの下に `pipelines/<NAME>/pipeline.yaml` を、コメント付きの骨組みとともに作成します。既存のディレクトリを上書きすることはなく、拒否します。

### `interactive`

```bash
deepzero interactive -w work/loldrivers/drivers-1a2b3c4d
```

| フラグ | デフォルト | 説明 |
|------|---------|-------------|
| `-m, --model` | `claude-code/claude-opus-5` | 対話に使うモデル。バックエンドが受け付けるモデル文字列であれば何でも指定できます。 |
| `-w, --work-dir` | `work` | コンテキストを読み込む実行ディレクトリ。 |
| `-v, --verbose` | off | 詳細ログ。 |

実行の状態をシステムプロンプトに読み込み、それについて質問できるようにする REPL です。`/status`、`/findings [filter]`、`/clear`、`/help`、`/quit` はローカルで処理され、それ以外はモデルに送られます。認識できない `/word` は、チャットの 1 ターンとして課金されるのではなく、そのまま報告されます。`/findings` は実行が記録したすべての検出結果を、引数に一致する行だけに絞り込んで、その実行を書いたパイプラインが宣言した語彙で列挙します。

`-w` には実行ディレクトリも、パイプラインのルートも指定できます。後者でコーパスが複数ある場合は、選んだコーパスの名前が示されます。デフォルトは文字どおり `work` で、これはパイプラインのディレクトリより上のルートにあたり、どの実行にも解決されません。その場合 REPL はその旨を伝え、実行を読み込んだふりをするのではなく実行のコンテキストなしで応答します。`-w` で目的の実行を指してください。

### `serve` と REST API

| フラグ | デフォルト | 説明 |
|------|---------|-------------|
| `--host` | `127.0.0.1` | バインドするホスト。ループバック以外を指定すると警告が表示されます。サーバーがネットワークから到達可能になるためです。 |
| `--port` | `8420` | バインドするポート。 |
| `-w, --work-dir` | `work` | 提供するワークディレクトリ。実行ディレクトリ、またはパイプラインのルート。後者の場合は最新のコーパスが提供され、その名前が示されます。 |

追加インストールが必要です: `pip install deepzero[serve]`。これにより Starlette と uvicorn が入ります。

> [!WARNING]
> **WIP / 実験的機能**
> REST API サーバーは現時点で未完成かつ非常に不安定であり、**使用すべきではありません**。あくまでローカルでの実験的な開発のためだけに提供されています。

実行状態とサンプルデータを問い合わせるための、読み取り専用の Starlette REST API を起動します。提供するのはちょうど 1 つの実行です。ワークディレクトリを 1 つのコーパスに解決するのが、リクエストが空で返ってきたあとではなく URL を表示する前なのは、そのためです。

| エンドポイント | メソッド | 説明 |
|----------|--------|-------------|
| `/api/health` | GET | ヘルスチェックと、提供中のワークディレクトリ |
| `/api/runs` | GET | 提供中の実行を要素 1 つのリストとして返す。なければ空のリスト |
| `/api/run` | GET | その実行の完全な状態。なければ 404 |
| `/api/samples` | GET | サンプルの一覧（`?verdict=`、`?classification=`、`?stage=`、`?status=` で絞り込み可能） |
| `/api/samples/{sample_id}` | GET | 過去のパイプラインデータを含む完全なサンプル状態 |
| `/api/samples/{sample_id}/artifacts/{name}` | GET | プロセッサが生成した特定のファイルアーティファクトを読み取り |

`verdict` はそのサンプルがパイプラインのどこを去ったかであり、`classification` はあるステージがそれについて何を結論したかです。応答にはどちらも含まれるため、それぞれ自分の名前どおりのフィールドを絞り込みます。`stage` はサンプルの現在のステージと一致するかを見ます。`status` は、履歴のいずれかのステージがそのステータスを持つサンプルを残します。パスの区切り文字を含むサンプル ID は拒否されます。ID はそのままファイルシステムのパスになり、このサーバーはすべてのインターフェースにバインドできるからです。
