## 同梱パイプライン

DeepZero には完全なパイプラインが 2 つ同梱されています。実際に実行するためのものであると同時に、現実の仕事をしているパイプライン定義がどのようなものかを読み解くための実例でもあります。

| パイプライン | コーパス | 何を探すか |
|----------|--------|-------------------|
| `pipelines/loldrivers` | ディスク上の Windows カーネルドライバー | BYOVD 候補。ハードウェアなしで到達できる IOCTL 表面 |
| `pipelines/source_audit` | git リポジトリ | 信頼できない入力から到達できるソースレベルの脆弱性 |

どちらも `model: claude-code/claude-opus-5` を宣言しているため、API キーなしで Claude Code のサブスクリプションを使って実行されます。任意の LiteLLM モデルを使うには `-m` で上書きしてください。[モデルの選択]({{ '/ja/reference/pipeline-yaml.html' | relative_url }})を参照してください。

## LOLDrivers パイプライン

リファレンスの BYOVD (Bring Your Own Vulnerable Driver) パイプラインは `pipelines/loldrivers/` に維持されています。

| ステージ | プロセッサ | 処理内容 |
|-------|-----------|--------------|
| `discover` | `pe_ingest/pe_ingest.py` | PE インジェストと LIEF ヘッダー解析 |
| `kernel_filter` | `metadata_filter` | IOCTL 表面を公開するカーネルモードドライバーに絞り込み、ハッシュで重複を排除 |
| `loldrivers_filter` | `loldrivers_filter/loldrivers_filter.py` | loldrivers.io に登録されている既知のエンティティを除外 |
| `decompile` | `ghidra_decompile/ghidra_decompile.py` | Ghidra を使ったヘッドレスデコンパイルの実行 |
| `semgrep_scanner` | `semgrep_scanner/semgrep_scanner.py` | 出力された C ソースコードに対する一括静的解析 |
| `rank_by_findings` | `top_k` | 生き残ったすべてのドライバーを検出結果の件数順に、多い方から並べ替え |
| `assess` | `generic_llm` | ドライバーごとに `assessment.j2` をレンダリングし、判定を記録 |

順位付けのステージはすべてを残し（`keep_top: 0`）、順序だけを変えます。これは意図的です。上位だけを残して他を捨てれば評価の呼び出しは節約できますが、どのドライバーが読む価値があるかを検出結果の件数で決めることになります。それはまさに、評価ステージが行うために存在する判断です。多い順に並べておけば、残りを捨てずに同じドライバーから先に検討でき、途中で止めた実行であっても、最も騒がしいドライバーに時間を使ったことになります。

除外をデコンパイルより前に置いているのは、同じ理由の裏返しです。Ghidra は群を抜いて高価なステージなので、安価なヘッダー検査やハッシュの照合で取り除いたドライバー 1 つ 1 つが、費やさずに済んだ数分になります。

### ハードウェアなしで検出結果を実際に動かせるか

多くのドライバーは、ハードウェアが列挙されて初めてデバイスオブジェクトを作成します。そのデバイスがないマシンや VM では `\.\<name>` が決して開かず、ドライバーが公開しているものには何一つ到達できません。しかもレポートだけを見ていると、それはドライバーが脆弱でないことと見分けがつきません。

`decompile` ステージは、デバイスオブジェクトがどこで作成されるかを記録します。

| 値 | 意味 |
|-------|---------|
| `device_created_in` | `IoCreateDevice` を呼び出している関数 |
| `device_on_load_path` | その関数が `DriverEntry` そのものか、あるいはそこから呼ばれるものか |

`device_on_load_path: true` は、そのドライバーを読み込むあらゆるマシンでデバイスが現れることを意味します。したがって、それに対する検出結果は今すぐ確認できます。`false` は、デバイスが別の場所、典型的には PnP の add-device や start-device のコールバックで作成されることを意味し、何かを確認するには実機が必要です。`IoCreateDevice` がまったく見つからない場合は、推測するのではなく、どちらも記録されません。

同梱パイプラインは `report.columns` に `decompile.device_on_load_path` を列挙しているため、各ドライバーに添えて表示されます。必要なのはそれだけです。この値はプロセッサの `provides` で宣言され、パイプラインが名指ししているだけで、レポートはデバイスオブジェクトが何であるかを知らないままです。

### デコンパイルがドライバーごとに書き出すもの

`decompile` ステージは、各サンプルの `decompiled/` ディレクトリに次を書き出します。

| ファイル | 内容 |
|------|----------|
| `dispatch_ioctl.c` | ディスパッチルーチン。1 度だけ記録されます |
| `ioctls/0xXXXXXXXX.c` | IOCTL コードごとに 1 つ。そのコードが何にデコードされるかを示し、上記のルーチンを指します |
| `ghidra_result.json` | メタデータ。デバイス名、シンボリックリンク、ディスパッチ名、および IOCTL コードごとのエントリ 1 件 |

1 つのドライバー内のすべてのコードは同じルーチンで処理されるため、ルーチンは 1 度だけ保存されて参照されるだけで、コードごとに複製されることはありません。`ioctl_handlers` のエントリが持つのは、コードとそのデコード結果のフィールド（`hex`、`device_type`、`function`、`method`、`access`）だけです。

サイズには目を配る価値があります。ここでの不具合は表に出ないからです。出力は正しく見えたまま、ただ巨大になります。目安として、デコンパイル済みドライバー 1,388 件のパックが生み出す `ghidra_result.json` は合計でおよそ **28 MB** です。同じコーパスに対してコードごとにルーチンを保存した場合は **734 MB** になり、単一のドライバーで 52 MB に達しました。ステージの実行結果がこれを桁違いに上回っている場合は、ルーチンを繰り返す状態に後退しています。そして評価ステージは、プロンプトを組み立てる際にその文書をドライバーごとに解析することになります。

`tests/test_extract_dispatch.py` がエントリの形を直接守っています。

### 前提条件

- Ghidra。`GHIDRA_INSTALL_DIR` を設定しておくこと。`JAVA_HOME` は設定されていれば読み取られます。
- PATH 上の `semgrep`: `pip install semgrep`。

## ソースコード監査パイプライン

git リポジトリを対象としたソースコード監査で、`pipelines/source_audit/` にあります。各リポジトリを 1 つのリビジョンで取得し、semgrep でスキャンしたうえで、本物の脆弱性と、コード中の形にルールが一致しただけのものとを切り分けることを役目とするモデルが読みます。

| ステージ | プロセッサ | 処理内容 |
|-------|-----------|--------------|
| `discover` | `git_ingest/git_ingest.py` | 各リポジトリを depth 1 でクローンするか、すでにディスク上にあるチェックアウトを読み取り、下流のすべてが判断の対象とするリビジョンを記録します |
| `size_filter` | `metadata_filter` | ソースコードを含まないチェックアウトと、スキャンする価値がないほど大きいツリーを除外します。2 つの名前で到達した同じコミットは 1 度だけスキャンされます |
| `scan` | `semgrep_scanner/semgrep_scanner.py` | 各チェックアウトに `rules/` を適用します。何も指摘されなかったリポジトリはここで止まります |
| `rank` | `top_k` | 生き残ったすべてのリポジトリを検出結果の件数順に、多い方から並べ替えます。除外はしません |
| `assess` | `generic_llm` | リポジトリごとに `assessment.j2` をレンダリングし、判定を記録します |

この 2 つの段階は、この順序であることに意味があります。semgrep は安価で、見るべき場所をすべて見つけます。そのほとんどは問題ありません。評価ステージは、検出結果が攻撃者の入力からシンクまでの経路を得るか、あるいは到達不能であると名指しで退けられるかが決まる場所です。

### 何を対象に指定するか

`deepzero run` が受け取るターゲットは 1 つで、インジェストステージはどちらの形も読み取ります。

- **ディレクトリ**: 直下の各サブディレクトリが 1 つのチェックアウトとして扱われます。何も取得しないため、非公開のコードがすでに置かれているマシンから外に出る必要はありません。それ自体がチェックアウトであるディレクトリは単一のリポジトリとして読まれます。`.git` のない単なるソースコードの置き場でも読み取られますが、その場合は報告できるリビジョンやオリジンがないだけです。
- **ファイル**: クローンするリポジトリのマニフェストとして読まれます。`#` によるコメントが使える 1 行 1 件のプレーンテキストか、リストとしての YAML、あるいは各エントリで ref を固定できる `repos:` キーを持つマッピングとしての YAML です。

```bash
# マニフェストに列挙されたリポジトリを監査する
deepzero run repos.txt -p pipelines/source_audit/pipeline.yaml

# または、すでにディスク上にあるチェックアウトのディレクトリを監査する
deepzero run C:\code\vendor -p pipelines/source_audit/pipeline.yaml
```

クローンはワークディレクトリではなく、インジェストステージ自身のキャッシュディレクトリに置かれます。そのため再実行にネットワークのコストはかからず、`--clean` でも捨てられません。

### ルールと言語

`rules/` には Python、JavaScript、TypeScript、Go、Java、Ruby、PHP、C# を対象とする 136 の semgrep ルールがあり、何を探すかによって分類されています。インジェクション、パストラバーサルと SSRF、認証と認可、暗号とシークレット、デシリアライゼーション、XSS とレスポンスヘッダーです。

一致していなければならない箇所が 3 つあります。ルール、`discover` の `extensions` リスト、そして `scan` の同一のリストです。この 3 つは互いに逆方向に失敗します。リストが取りこぼした拡張子は、数えられもスキャンされもしないため、そのリポジトリは実態よりも小さく、きれいに見えます。逆に、どのルールも対象としない拡張子がリストにあると、そのファイルは走査され、数えられ、決して一致しえないスキャンのために用意されます。言語を追加するとは 3 つすべてを直すことであり、それらが食い違うと `tests/test_source_audit_pipeline.py` が失敗します。

したがって、`rules/` が対象としない言語で書かれたリポジトリはソースファイル数がゼロと数えられ、`size_filter` で除外されます。これは「ソースコードがない」と読めますが、意味しているのは「このパイプラインが監査できるものがここにはない」です。それでも、この結果になるのが望ましいと言えます。ツリーはクローンの 1 ステージ後に除外され、決して発火しえないルールでのスキャンのために用意されることがないからです。

### レポートの読み方

このパイプラインは自らの語彙を宣言しています。リポジトリはディスク上のファイルではないからです。

```yaml
report:
  title: Source repository audit
  entity: repository
  entity_plural: repositories
  target_label: organisation
  vulnerable_when: [vulnerable]
  safe_when: [not exploitable]
```

`vulnerable_when` を絞り込んでいるのには、知っておく価値のある理由があります。評価は `[VULNERABLE]` または `[NOT EXPLOITABLE]` を返しますが、デフォルトの肯定側リストには `exploitab` が含まれており、これは否定側の判定に含まれています。[判定の照合方法]({{ '/ja/reference/pipeline-yaml.html' | relative_url }})を参照してください。

このパイプラインの `columns` は、検出結果の件数、スキャンされたファイル数、ソースファイル数、主要言語、リビジョンを各リポジトリに添えます。スキャンされたファイル数がそこにあるのには理由があります。検出結果のないリポジトリと、semgrep が 1 つもファイルを開かなかったリポジトリは、どちらも検出結果ゼロと表示されますが、結果と呼べるのはそのうち一方だけだからです。

### 前提条件

- `discover` ステージのための、PATH 上の `git`。
- PATH 上の `semgrep`: `pip install semgrep`。

長い実行に踏み切る前に、どちらのパイプラインについても、これらをまとめて確認できます。

```bash
deepzero validate pipelines/source_audit/pipeline.yaml
```
