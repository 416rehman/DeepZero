## Встроенные процессоры

Указываются простым именем. Выполните `deepzero list-processors`, чтобы увидеть их вместе с реализующими классами.

| Идентификатор | Тип | Функциональность |
| ------------- | --- | ---------------- |
| `file_discovery` | Ingest | Рекурсивный обход файловой системы и криптографическое хеширование. |
| `metadata_filter` | Map | Проверка равенства полей через `require:`, числовые пороги через любой ключ `min_<field>` / `max_<field>` и дедупликация через `dedup_field`. Поля читаются из объединенных данных всех вышестоящих этапов. |
| `hash_exclude` | Map | Криптографическое исключение с помощью встроенных списков или плоских файлов. |
| `generic_llm` | Map | Рендеринг шаблонов Jinja2, вызов LLM и парсинг ответов. |
| `generic_command` | Map | Произвольное выполнение shell-команд с подстановкой контекстных переменных. |
| `top_k` | Reduce | Усечение набора образцов на основе числовых скалярных значений. |
| `sort` | Reduce | Детерминированное переупорядочивание образцов без сокращения набора данных. |

Порог `min_<field>` читает поле, которого не записал ни один вышестоящий этап, как ноль и отфильтровывает образец. Для действительно отсутствующего поля это правильный ответ, а для переименованного неправильный, поэтому если этап внезапно отфильтровал целый корпус за считанные секунды, стоит сверить имена с тем, что фактически предоставляют вышестоящие этапы.

## Внешние процессоры в комплекте

Они лежат в `processors/` и указываются по пути, поэтому читаются как обычные внешние процессоры, а не как привилегированные встроенные. Именно их используют [встроенные конвейеры]({{ '/ru/reference/included-pipeline.html' | relative_url }}). `ghidra_decompile`, `git_ingest` и `loldrivers_filter` объявляют принимаемые ключи датаклассом `Config`, поэтому их список и есть исходный код, а ключ, написанный в конвейере с опечаткой, будет отмечен, а не проигнорирован. `pe_ingest` и `semgrep_scanner` читают сырой словарь конфигурации, где ключ с опечаткой не будет ни прочитан, ни отмечен. Рядом с исходниками каждого лежит README с описанием того, что он записывает, и тех особенностей поведения, которые читателя удивят.

| Путь | Тип | Функциональность |
| ---- | --- | ---------------- |
| `pe_ingest/pe_ingest.py` | Ingest | Обнаруживает файлы PE, разбирает заголовки и извлекает метаданные драйверов. |
| `git_ingest/git_ingest.py` | Ingest | Превращает git-репозитории в образцы, из каталога с копиями или из манифеста URL. |
| `loldrivers_filter/loldrivers_filter.py` | Map | Исключает образцы, чей SHA-256 совпадает с известной записью в базе loldrivers.io. |
| `ghidra_decompile/ghidra_decompile.py` | Map | Безголовая декомпиляция Ghidra с настраиваемым постскриптом. |
| `semgrep_scanner/semgrep_scanner.py` | BulkMap | Пакетное сканирование semgrep по активным образцам. |

### `git_ingest`

Один образец соответствует одному репозиторию, а его `source_path` указывает на корень рабочей копии, то есть ровно на то, на что нужно направлять сканер исходного кода. Цель, переданная в CLI, всегда является реальным путем, поэтому обе формы входных данных сохраняют работу возобновления и разделения по корпусам: каталог читается как контейнер рабочих копий и ничего не загружается, а файл читается как манифест, и каждая его запись клонируется.

`sample_id` выводится из идентичности репозитория, а не из пути, поэтому один и тот же репозиторий, полученный через манифест и через каталог, остается одним и тем же образцом, и повторный запуск сохраняет его результаты.

### `semgrep_scanner`

| Поле | По умолчанию | Значение |
|-------|---------|---------|
| `rules_dir` | нет, обязателен | Каталог правил semgrep, которые нужно загрузить. |
| `target_dir` | `decompiled` | Подкаталог рабочего каталога самого образца, который нужно сканировать. Задайте `""`, и вместо этого будет просканирован путь самого образца. |
| `extensions` | `.c`, `.h`, `.cpp`, `.py` | Какие файлы передаются semgrep. Ведущая точка добавляется, если ее нет, а одиночная строка принимается как список из одного элемента. |
| `batch_size` | `200` | Сколько образцов приходится на один вызов semgrep. `0` или меньше отправляет весь этап одним прогоном. |
| `timeout` | `300` | Сколько секунд отводится процессу semgrep на один пакет. |
| `min_findings` | `0` | Отфильтровать образец, у которого находок меньше этого числа. `0` не фильтрует ничего. |

Именно `target_dir` и `extensions` позволяют одному сканеру обслуживать оба встроенных конвейера. Значения по умолчанию подходят конвейеру, который сперва декомпилирует и пишет C рядом с каждым образцом. Конвейер, чьи образцы уже являются исходным кодом, например рабочей копией репозитория, задает `target_dir: ""` и расширяет `extensions` до того, что он действительно принял.

`rules_dir` разрешается сначала относительно рабочего каталога, затем относительно каталога конвейера, причем и `validate()`, и само сканирование разрешают его одинаково, потому что однажды разное разрешение позволило проверке пройти, пока сканирование шло вообще без загруженных правил. `rules_dir`, которого нет на момент выполнения этапа, роняет все образцы в нем, вместо того чтобы сканировать с пустым набором правил и отчитаться о чистом корпусе.

#### Уже лежащий на диске findings.json подхватывается, а не пересканируется

Это самое неожиданное здесь. До того как что-либо сканировать, процессор ищет `findings.json` в собственном каталоге каждого образца. Если файл есть и он разбирается, эти находки принимаются за результат, образец записывается с `findings_cached: true`, и semgrep о нем вообще не спрашивают. Если файл нечитаем, образец сканируется заново.

Именно это не дает прерванному запуску повторять пакеты, которые он уже отработал. Это же означает, что правка правил и повторный запуск сами по себе ничего не меняют: старый файл на месте, поэтому возвращаются старые находки. Заставить сканировать по-настоящему можно через `deepzero run --redo <этап>`, и это работает потому, что `findings.json` записывается артефактом на каждом пути, который его пишет, включая путь с фильтрацией, так что `--redo` может найти файл и удалить его.

Подхваченный результат несет только `finding_count` и `findings_cached`. `files_submitted` и `files_scanned` приходят из самого прогона semgrep, поэтому у образца, который в этот раз не сканировался, нет ни того, ни другого.

#### Пакеты и сбои, о которых стоит знать

Образцы сканируются пакетами, а не за один прогон, поэтому пакет, который превысил время ожидания или вернул нечитаемый результат, стоит только своих образцов, а не всего корпуса, работа над которым уже проделана. Пакет, вышедший за `timeout`, записывает как сбойные все свои образцы.

`extensions` и правила должны быть согласованы. Файл, чье расширение не перечислено, никогда не попадет в semgrep, сколько бы правил ему ни соответствовало, и этот сбой происходит молча: сканирование сообщает о нуле находок, что неотличимо от чистого дерева. Именно поэтому конвейер аудита исходного кода записывает `files_scanned` рядом с `finding_count`.

Еще два исхода отклоняются, а не выдаются за чистый результат, потому что снаружи оба выглядят ровно как чистый корпус: semgrep вернулся с ошибками загрузки и вовсе без результатов, и semgrep не перечислил ни одного из переданных ему файлов. Оба роняют пакет и говорят об этом.

Образец, чьего `target_dir` нет на диске, падает сам по себе, до того как собран хоть один пакет, и сообщение спрашивает, выполняется ли этап, который производит этот каталог, до текущего, а это и есть обычный ответ.

`min_findings` фильтрует образец на этом этапе, а не роняет его, поэтому образец покидает запуск с записанной причиной и с прикрепленным `findings.json`. Оба встроенных конвейера ставят `min_findings: 1`, и именно это не дает образцу, на котором ничего не отмечено, стоить вызова модели дальше по конвейеру.
