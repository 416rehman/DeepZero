## Конфигурация Конвейера

**Конвейер (Pipeline)** в DeepZero — это декларативный граф выполнения, определяющий непрерывный отказоустойчивый процесс преобразования данных. Он превращает сырой физический набор данных в набор аналитический, с высокой долей полезного сигнала.

Схема конвейера строго определена в YAML. DeepZero разрешает конфигурацию динамически, поддерживая раскрытие переменных в стиле shell (например, `${VAR:-default}`).

### Схема Конфигурации

```yaml
name: my_pipeline
description: Стандартный конвейер поиска уязвимостей
version: "1.0"
model: openai/gpt-4o  # схема выбирает бэкенд, см. ниже

settings:
  work_dir: work
  max_workers: 8  # общий потолок числа потоков ThreadPoolExecutor

stages:
  # Этап 1: ОБЯЗАН быть IngestProcessor
  - name: discover
    processor: file_discovery
    config:
      extensions: ["*"]

  # Этап 2: синхронный фильтр
  - name: filter
    processor: metadata_filter
    config:
      require:
        is_executable: true

  # Этап 3: обработка Map с высокой задержкой
  - name: decompile
    processor: ghidra_decompile/ghidra_decompile.py
    parallel: 4           # ограничивает параллелизм четырьмя одновременными JVM Ghidra
    timeout: 300          # бюджет на образец: этап перестает ждать через 300 секунд
    on_failure: skip      # обрабатывает исключения молча, не прерывая работу (skip, retry, abort)
    max_retries: 2        # ограничение на число повторов
    config:
      ghidra_install_dir: ${GHIDRA_INSTALL_DIR}
```

### Параметры Этапов

Каждый этап, определенный в массиве `stages:`, принимает следующие атрибуты:

| Поле | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `name` | string | `stage_N` | Уникальное имя этапа внутри конвейера |
| `processor` | string | требуется | Ссылка на процессор (см. ниже) |
| `config` | dict | `{}` | Настройки конкретного процессора |
| `parallel` | int | `4` | Параллелизм для Map процессоров. `0` масштабируется автоматически, в пределах ограничений ниже |
| `timeout` | int | `0` | Бюджет на образец в секундах для этапов Map (0 = без бюджета) |
| `on_failure` | string | `skip` | Задает поведение при сбое: `skip`, `retry` или `abort` |
| `max_retries` | int | `0` | Число повторов при `on_failure: retry` |
| `limit` | int | `0` | Лежит внутри `config` и читается движком: усекает уцелевший корпус после этого этапа (0 = оставить все) |

#### `parallel`

`parallel: 0` означает «автоматически», а не «без ограничений». Исполнитель начинает с
`os.cpu_count()` и затем понижает это число дважды: до потолка, который процессор
объявляет в `max_parallelism()`, и до настройки `max_workers` конвейера, смотря что
меньше. Процессор, поднимающий на каждый образец отдельную JVM или внешний инструмент,
объявляет этот потолок именно затем, чтобы оставленное по умолчанию `parallel: 0` не
исчерпало машину, и запуск пишет в лог, какое из ограничений сработало. Явное
`parallel: N` соблюдается ровно так, как написано, и не ограничивается ни тем, ни другим.

#### `timeout`

`timeout` является бюджетом, который один образец получает на этапе Map. Когда бюджет
исчерпан, этап перестает ждать, записывает этот образец как исчерпавший время и переходит
к следующему.

Чего он не делает, так это никого не убивает. В Python ничто не может остановить уже
работающий поток, поэтому рабочий поток самого процессора бросают, а не завершают:
запущенный им внешний процесс продолжает работать, пока не закончит сам, а память,
которую этот поток держит, остается занятой до его возврата. Бюджет ограничивает, сколько
ждет *этап*, а не сколько длится работа. Процессор, вызывающий внешние программы, должен
передать ограничение и самому инструменту, как это делает `semgrep_scanner` собственным
ключом конфигурации `timeout`.

Покрыты только этапы Map. Этапы reduce и bulk-map выполняются одним вызовом на весь
корпус, а не по вызову на образец, и ни один из них под этим бюджетом не работает.

Исчерпание времени не является сбоем, поэтому `on_failure: retry` его не повторяет, а
возобновленный запуск оставляет такой образец в покое, потому что бюджет, которого не
хватило, остался прежним. Попросить о новой попытке нужно через
[`--retry-timeouts`]({{ '/ru/reference/cli.html' | relative_url }}).

#### `limit`

`limit` лежит внутри блока `config` этапа, но читает его движок, а не процессор, поэтому
его можно задать на любом этапе независимо от того, что этот процессор принимает, и
процессор с типизированным `Config` не предупредит, что ключ ему неизвестен.

Как только этап завершится, каждый еще активный образец после первых `limit` штук
помечается отфильтрованным на этом этапе и дальше в запуске не участвует. Счет идет по
всему уцелевшему корпусу, а не по образцам, которых коснулся именно этот этап.

Порядок берется тот, в котором запуск сейчас несет корпус, и именно поэтому `limit` имеет
смысл ставить на этап reduce или на следующий за ним. Reduce возвращает уцелевших
ранжированными, исполнитель принимает этот порядок до усечения, и тогда `limit` оставляет
самых высокоранговых, а не произвольный срез. На этапе, за которым ранжирования не было,
он оставит те образцы, которые просто окажутся первыми.

### Поля Верхнего Уровня

| Поле | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `name` | string | имя каталога конвейера | Задает имя конвейера и имя его рабочего каталога |
| `description` | string | `""` | Свободный текст |
| `model` | string | `""` | Модель для всех этапов LLM. Конвейеру без этапов LLM она не нужна; `deepzero validate` предупреждает, когда она отсутствует |
| `settings` | dict | `{}` | `work_dir` (по умолчанию `work`) и `max_workers` (по умолчанию `min(4, cpu_count)`) |
| `knowledge` | dict | `{}` | Произвольные значения уровня конвейера, доступные любому процессору через `ctx.get_knowledge(key)` |
| `report` | dict | `{}` | Как `deepzero report` представляет результаты этого конвейера, см. ниже |
| `stages` | list | требуется | Хотя бы один, причем первый обязан быть процессором приема |

`work_dir` является корнем, а не каталогом запуска. Запуск попадает в
`<work_dir>/<pipeline name>/<corpus key>/`, где ключ корпуса выводится из пути цели,
поэтому два корпуса, прошедшие через один конвейер, никогда не пересекаются и каждый
возобновляется сам по себе. См. [справочник CLI]({{ '/ru/reference/cli.html' | relative_url }}).

### Выбор Модели

Часть `model` до первого `/` является схемой, и именно она выбирает бэкенд:

| Строка модели | Бэкенд |
|--------------|---------|
| `claude-code`, `claude-code/<model-id>` | Локально установленный CLI Claude Code, в котором вы уже авторизованы |
| все остальное, например `openai/gpt-4o`, `gemini/...`, `gpt-4o` | LiteLLM, который покрывает все поддерживаемые им конечные точки с ключом API |

`claude-code` выполняет конвейер через подписку Claude Code без ключа API. DeepZero
никогда не работает с учетными данными для него: он вызывает CLI, в который вы уже
вошли, и наследует ту авторизацию, которая есть у этого бинарника. Часть после слэша
передается как модель, поэтому `claude-code/claude-opus-5` выбирает конкретную модель, а
голое `claude-code` оставляет CLI на его модели по умолчанию. Оба поставляемых конвейера
объявляют модель `claude-code`, и `-m` переопределяет ее на один запуск.

Поскольку эти вызовы несут недоверенное содержимое, вывод декомпилятора и исходный код,
вытянутый из чужих репозиториев, CLI вызывается с запрещенными инструментами и серверами
MCP. Для завершения запроса они не нужны, а если оставить их включенными, внедренный
промпт получил бы доступ к shell.

Реестр открыт: `register_backend()` добавляет схему без правки DeepZero, и чтобы получить
новую, ничего менять не нужно ни в провайдере, ни в конвейере, ни в этапах. Любая схема,
которую не занял ни один бэкенд, уходит в LiteLLM.

Какой бы бэкенд ни был выбран, у него спрашивают, может ли он вообще работать, до того
как он понадобится этапу: `deepzero validate` проверяет ключ API для модели LiteLLM и
наличие бинарника для агентского CLI, а [`deepzero run --preflight`]({{ '/ru/reference/cli.html' | relative_url }})
идет дальше и подтверждает, что в CLI выполнен вход.

### Логика Разрешения (`engine/registry.py`)

Форма значения `processor:` определяет, как оно разрешается, поэтому ссылка никогда не
бывает неоднозначной между внешним файлом и встроенным именем:

| Ссылка | Как разрешается |
|-----------|-------------|
| Содержит `/` или `\`, например `ghidra_decompile/ghidra_decompile.py` | Файл в `processors/` внутри рабочего каталога. Используется первый подкласс Processor в нем, сами базовые классы игнорируются |
| То же самое с добавленным `:ClassName` | Именно этот класс в этом файле, что и нужно файлу, определяющему более одного процессора |
| Простое имя, например `metadata_filter` | Внутренний реестр, наполняемый в `stages/__init__.py` |
| Простое имя, содержащее `:`, например `my.python.module:MyClass` | Импортируемый модуль на `sys.path` и класс внутри него |

Все остальное является ошибкой с перечислением встроенных процессоров, а не сбоем позже
по ходу запуска. Обратите внимание, что внешние пути разрешаются относительно рабочего
каталога, а не каталога конвейера, поэтому поставляемые конвейеры запускаются из корня
репозитория.

### Динамическое Раскрытие

До того как проверка схемы свяжет процессоры, DeepZero обходит все дерево DOM YAML, вычисляя совпадения регулярного выражения `\$\{([^}]+)\}`. Переменные окружения определяют итоговую конфигурацию выполнения. Это явным образом не дает жестко зашивать ключи API или каталоги установки в закоммиченные `.yaml` конвейеров.

### Значения для Промптов

Этап, чей `config` содержит `prompt`, рендерит этот файл как шаблон Jinja. Значением
может быть путь или имя файла, лежащего рядом с конвейером; в любом случае файл
загружается, а не используется как сам текст промпта.

Любому промпту доступны эти значения:

| Значение | Тип | Описание |
|-------|------|-------------|
| `sample_name` | string | Имя файла образца в том виде, в каком его записал этап приема |
| `sample_path` | string | Абсолютный путь к образцу на диске |
| `history` | dict | `{stage_name: data}` по каждому уже отработавшему этапу |
| `config` | dict | Собственный блок `config` этого этапа |

Помимо них промпт может использовать все, что записали этапы **до него**. Каждый
процессор объявляет эти имена в своем атрибуте `provides`, и они бывают двух видов:

- **Ключи данных**: все, что процессор кладет в `data`, например `device_name` или
  `finding_count`. Доступны напрямую под этим именем, а также через `history`.
- **Артефакты**: файл, записанный процессором, доступный по своему пути, в имя
  которого свернуты разделители и расширение. `decompiled/dispatch_ioctl.c` становится
  `decompiled_dispatch_ioctl_c`. JSON разбирается в объект, а длинный список расширений
  исходного кода, разметки и обычного текста приходит текстом; этапу, которому нужен
  другой набор, достаточно объявить `text_extensions` в своем `config`, и этот список
  заменит стандартный, а не дополнит его. Ничего другого не предоставляется. Текст сверх
  бюджета контекста, то есть `max_context_tokens`, умноженного на четыре символа,
  усекается и сообщает об этом, а файл JSON больше этого бюджета пропускается с
  предупреждением, а не разбирается.

Значение доступно только этапам *после* того, который его записал, поэтому промпт не
может дотянуться до вывода собственного этапа.

Чтобы увидеть, что предлагает конкретный конвейер, выполните:

```bash
deepzero validate <pipeline>
```

Промпт, называющий то, чего не производит ни один предшествующий этап, выдается как
ошибка с перечислением того, что было доступно вместо этого. Рендеринг во время запуска
строг ровно к тому же, поэтому этап, до которого дело все-таки дошло, завершается сбоем
на этом образце, а не отправляет промпт дальше. Это важно, потому что иначе неизвестное
имя отрендерилось бы в пустоту: модель попросили бы судить о пустых данных, и вердикт
вернулся бы уверенным и бессмысленным.

### Блок report

`deepzero report` строится на том, что гарантирует движок, а гарантирует он одно и то же
для любого конвейера: каждый этап записывает `data`, `artifacts` и статус. Различается
словарь терминов. Конвейер по драйверам ядра, аудит исходного кода и проверка лицензий
дают исходы одинаковой формы и называют их совершенно по-разному.

Поэтому формы зафиксированы, а слова объявляются:

```yaml
report:
  title: Source repository audit
  entity: repository
  entity_plural: repositories
  target_label: organisation
  classification_key: classification
  positive_when: [vulnerable]
  negative_when: [not exploitable]
  columns:
    - scan.finding_count
    - discover.primary_language
  findings_files: [findings.json]
```

Все поля необязательны, и каждое значение по умолчанию воспроизводит то поведение,
которое было у конвейера до появления этого блока. Конвейер, не объявивший ничего, все
равно получает пригодный отчет.

| Поле | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `title` | string | `<имя конвейера> results` | Заголовок `index.html` |
| `entity` | string | `sample` | Как называется один результат в интерфейсе |
| `entity_plural` | string | `entity` + `s` | Нужно только там, где добавление s неверно, например repository |
| `target_label` | string | `corpus` | На что был направлен запуск |
| `classification_key` | string | `classification` | Ключ в `data` этапа, содержащий заключение |
| `positive_when` | list | `vulnerab`, `exploitab`, `confirmed` | Значения, считаемые за то, что вы ищете |
| `negative_when` | list | `safe`, `not vulnerab`, `benign`, `clean` | Значения, считаемые за то, что ничего не найдено |
| `columns` | list | подбирается автоматически | Значения вида `stage.key`, показываемые напротив каждого результата |
| `findings_files` | list | `findings.json` | Имена файлов в каталоге образца, из которых читаются находки |
| `lexicon` | dict | см. ниже | Слова для исходов |

`vulnerable_when` и `safe_when` принимаются как прежние имена для `positive_when` и
`negative_when` и означают ровно то же самое. Если заданы оба, побеждает `positive_when`.

`target_label` не зря занимает свое место: значение по умолчанию, «corpus», предполагает
кучу файлов на диске. У запуска по работающему приложению есть область охвата, у запуска
по репозиториям организации есть организация, и назвать любое из этого корпусом читается
как ошибка в отчете, который откроет кто-то другой.

#### Как сопоставляется вердикт

Значение, записанное под `classification_key`, приводится к нижнему регистру и сначала
проверяется на подстроки из `positive_when`, затем на подстроки из `negative_when`.
Именно подстроки, а не точные значения, поэтому `vulnerab` покрывает и «vulnerable», и
«vulnerability».

Проверка положительных первыми и объясняет, зачем переопределять значения по умолчанию.
Конвейер, чей отрицательный вердикт равен `[NOT EXPLOITABLE]`, содержит `exploitab`,
которое входит в положительные по умолчанию, поэтому был бы засчитан как попадание.
Сужение `positive_when` до `[vulnerable]` и делает поставляемый аудит исходного кода, и
это первое, что стоит проверить, когда вердикты самого запуска расходятся с подсчетами
отчета.

Вердикт, не совпавший ни с одним списком, не отбрасывается молча. Он попадает в «Unclear
verdict», а это совсем не то же утверждение, что признание безопасным.

#### Колонки

`columns` называет значения вида `stage.key`, используя имя этапа из этого конвейера, и
ставит каждое напротив каждого результата. Объявляйте те, которые решают, что читать
дальше: можно ли вообще воспроизвести находку, сколько кода было реально просканировано,
какая ревизия оценивалась. Когда не объявлено ничего, отчет сам берет до шести числовых
или интересно названных ключей из того, что записал запуск.

Ничего добавлять в отчет для этого не нужно. Ключ становится доступен в тот момент,
когда процессор записал его в `data`, а конвейер назвал его здесь.

#### Находки

`findings_files` называет файлы внутри каталога каждого образца, из которых читаются
находки. Любой артефакт JSON, чье содержимое выглядит как список находок, подхватывается
тоже, поэтому процессор, пишущий под другим именем, все равно попадет в отчет без
настройки.

#### Словарь терминов

У отчета есть одна корзина для того, что ищут, одна для находок, по которым ничего не
решено, и одна для результата, проанализированного до конца и ничем не отмеченного. Это
структура. Вашими являются только их названия:

| Поле | По умолчанию | Где появляется |
|-------|---------|------------------|
| `discipline` | `vulnerability research` | Рядом с названием продукта в шапке |
| `positive` | `Vulnerable` | Подпись корзины и ее фильтра |
| `positive_help` | `an assessment stage concluded these are vulnerable` | Пояснение, показываемое рядом с этой подписью |
| `positive_phrase` | `assessed as vulnerable` | Завершает «12 repositories ...» в строке сводки |
| `nothing_positive` | `Nothing was confirmed vulnerable` | Заголовок, когда запуск не нашел ничего, с чем нужно что-то делать |
| `unconfirmed` | `Needs assessment` | Находки есть, но ни одна оценка по ним не вынесена |
| `negative` | `Clear` | Проанализировано до конца, ничего не отмечено |

Остальные исходы именует движок, и они не настраиваются, потому что описывают то, что
сделал движок, а не то, что искал конвейер: «Errored», «Ran out of time», «Unclear
verdict» и «Filtered out».

Каждый ключ читается сам по себе, поэтому объявление одного оставляет остальные на
значениях по умолчанию. Ключ, которого нет среди семи перечисленных, игнорируется, как и
оставленный пустым, а `lexicon:`, записанный значением, а не блоком, целиком откатывается
к значениям по умолчанию, вместо того чтобы обрушить отчет, который долгий запуск только
что заработал.

Итоговые формулировки записываются в `report.json` рядом со счетчиками, как
`bucket_labels`, `entity`, `entity_plural` и `target_label`, поэтому все, что рисует
собственные заголовки по этому файлу, называет каждый исход так же, как HTML.

Именно это выводит инструмент за пределы поиска уязвимостей. У конвейера, проверяющего
лицензии зависимостей, те же три исхода и ни одного из слов по умолчанию для них,
поэтому он говорит, что это такое:

```yaml
report:
  entity: package
  target_label: dependency tree
  classification_key: licence_status
  positive_when: [incompatible]
  negative_when: [compatible]
  lexicon:
    discipline: licence compliance
    positive: Incompatible
    positive_help: the declared licence conflicts with this project's
    positive_phrase: carry an incompatible licence
    nothing_positive: No incompatible licences were found
    unconfirmed: Needs a decision
    negative: Compatible
```

Больше ничего не меняется. Отчет по-прежнему ранжирует, фильтрует, группирует и
экспортирует ровно так же, как для охоты на драйверы, потому что ничто из этого никогда
не зависело от того, о чем был запуск.

### Отметки Проверки

Конвейер записывает то, к чему он пришел. Проверил ли это заключение человек, является
отдельным утверждением, и сделать его может только читатель, поэтому отчет несет
отметки, которые тот проставляет по ходу чтения.

На странице любого результата их две, потому что проверка либо пришла к ответу, либо нет
(подписи в отчете английские):

| Отметка | Означает |
|------|-------|
| **Confirmed** | проверено, и держится |
| **Refuted** | проверено, и не подтвердилось |

Любая из двух открывает заметку о том, что вы запускали, на чем и что произошло, чтобы
кто-то другой мог повторить попытку. Заметка принадлежит отметке: результату без отметки
некуда ее положить, поэтому проверка, ничего не решившая, записывается тем, что результат
оставляют как есть, а не записью о том, до чего она дошла.

Все, что не несет ни одной из двух отметок, считается **Unreviewed**, независимо от того,
никто его не открывал или кто-то открывал и не смог ничего решить. Когда-то это были
отдельные элементы управления, и рядом друг с другом они читались как одно и то же.

Refuted намеренно не сливается с Unreviewed. Это законченная работа с определенным
ответом, и результат, который не подтвердился, никогда не должен выглядеть как тот,
которого никто не разбирал.

Отметки появляются напротив каждой строки в индексе, и по ним можно фильтровать, включая
Unreviewed, что и дает список результатов, по которым еще никто не вынес решения. Сводка
считает все три состояния, поэтому запуск читается как то, что действительно известно, а
не только как то, что было заявлено.

Отчет является файлом, поэтому отметки живут в браузере. **Export marks** выгружает их в
`marks.json`; сохраните его рядом с `index.html`, и они станут частью отчета: будут
отрисованы для всех, кто его откроет, и попадут в `inventory.csv` как `review` и
`review_note`. Отметки привязаны к конвейеру и цели, а не к пути файла, поэтому повторный
прогон по тому же корпусу их сохраняет.
