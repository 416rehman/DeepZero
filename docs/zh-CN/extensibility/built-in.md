## 内置处理器

通过裸名称引用。执行 `deepzero list-processors` 可以看到它们及其实现类。

| 标识符 | 类型 | 功能 |
| ---------- | ---- | ------------- |
| `file_discovery` | 摄取 (Ingest) | 递归文件系统遍历与加密哈希。 |
| `metadata_filter` | 映射 (Map) | 通过 `require:` 进行字段相等判断，通过任意 `min_<field>` / `max_<field>` 键进行数值阈值判断，并通过 `dedup_field` 去重。字段取自上游各阶段合并后的数据。 |
| `hash_exclude` | 映射 (Map) | 针对内联列表或纯文本文件的加密排除过滤，通过 `dedup` 在运行内去重，并通过 `hash_field` 指定从哪个字段读取哈希 (未设置时为 `sha256`)。 |
| `generic_llm` | 映射 (Map) | Jinja2 模板渲染、LLM 调用与响应解析。 |
| `generic_command` | 映射 (Map) | 带有上下文变量替换的任意 Shell 执行。 |
| `top_k` | 归约 (Reduce) | 基于数值标量截断样本集。 |
| `sort` | 归约 (Reduce) | 在不减少数据集的情况下对样本进行确定性重新排序。 |

`min_<field>` 阈值会把上游任何阶段都未记录过的字段读作零，从而过滤掉该样本。对于确实不存在的字段这是正确答案，而对于被改了名的字段则是错误答案，因此当某个阶段突然在几秒内过滤掉整个语料库时，值得对照上游实际提供的名称检查一下。

## 内置的外部处理器

它们位于 `processors/` 中并通过路径引用，因此被当作普通的外部处理器读取，而不是享有特权的内置处理器。[内置流水线]({{ '/zh-CN/reference/included-pipeline.html' | relative_url }}) 使用的正是它们。`ghidra_decompile`、`git_ingest` 和 `loldrivers_filter` 用一个 `Config` 数据类声明了自己接受的键，因此源码本身就是那份清单，流水线里写错的键会被报告出来而不是被忽略。`pe_ingest` 和 `semgrep_scanner` 读取的是原始配置字典，其中写错的键既不会被读取，也不会被报告出来。每个处理器的源码旁都附有一份 README，说明它写出什么，以及读者会感到意外的那些行为。

| 路径 | 类型 | 功能 |
| ---- | ---- | ------------- |
| `pe_ingest/pe_ingest.py` | 摄取 (Ingest) | 发现 PE 文件、解析头部并提取驱动程序元数据。 |
| `git_ingest/git_ingest.py` | 摄取 (Ingest) | 把 git 仓库变成样本，来源可以是一个存放检出目录的目录，也可以是一份 URL 清单。 |
| `loldrivers_filter/loldrivers_filter.py` | 映射 (Map) | 排除 SHA-256 命中 loldrivers.io 数据库中已知条目的样本。 |
| `ghidra_decompile/ghidra_decompile.py` | 映射 (Map) | Ghidra 无头反编译，后处理脚本可配置。 |
| `semgrep_scanner/semgrep_scanner.py` | 批量映射 (BulkMap) | 对当前活动样本进行批量 semgrep 扫描。 |

### `git_ingest`

一个样本就是一个仓库，它的 `source_path` 是检出目录的根，而这正是源码扫描器希望被指向的位置。CLI 目标始终是一个真实路径，因此两种输入形态都能让恢复和语料库作用域继续正常工作：目录会被读作检出目录的容器，什么都不会被拉取；文件则会被读作清单，其中每一条都会被克隆。

`sample_id` 派生自仓库自身的身份而非路径，因此同一个仓库无论是经由清单还是经由目录抵达，都是同一个样本，重新运行也会保留它的结果。

### `semgrep_scanner`

| 字段 | 默认值 | 含义 |
|-------|---------|---------|
| `rules_dir` | 无，必填 | 要加载的 semgrep 规则所在目录。 |
| `target_dir` | `decompiled` | 样本自身工作目录下要扫描的子目录。把它设为 `""`，则改为扫描样本自身的路径。 |
| `extensions` | `.c`, `.h`, `.cpp`, `.py` | 哪些文件会被交给 semgrep。缺少前导点时会自动补上，单个字符串会被当作只有一项的列表。 |
| `batch_size` | `200` | 每次调用 semgrep 处理多少个样本。取 `0` 或更小则把整个阶段放进一次运行。 |
| `timeout` | `300` | 一批的 semgrep 进程被允许运行的秒数。 |
| `min_findings` | `0` | 发现数少于此值的样本会被过滤掉。`0` 表示不过滤任何样本。 |

`target_dir` 和 `extensions` 正是让同一个扫描器能服务于两条内置流水线的原因。默认值适合先反编译、再在每个样本旁写出 C 代码的流水线。若某条流水线的样本本身就是源码，例如一个仓库检出，则应设置 `target_dir: ""`，并把 `extensions` 放宽到它实际摄取的那些扩展名。

`rules_dir` 先相对于工作目录解析，再相对于流水线目录解析，而且 `validate()` 和扫描本身用的是同一套解析方式，因为曾经两边解析方式不一致，导致验证通过、扫描却在没有加载任何规则的情况下跑了起来。阶段运行时若 `rules_dir` 并不存在，该阶段中的每个样本都会失败，而不是在什么都没加载的情况下扫描，然后报告出一个干净的语料库。

#### 磁盘上已有的 findings.json 会被直接采纳，而不是重新扫描

这是最出人意料的一点。在扫描任何东西之前，处理器会先在每个样本自身的目录里查找 `findings.json`。如果它存在，引擎报告缓存下来的结果依然有效，并且该文件能解析，那些发现就会被当作结果采纳，该样本会以 `findings_cached: true` 记录下来，semgrep 根本不会被问到它。有效与否不归处理器判断：引擎会把本阶段当前的指纹，与上一次结果被记录时所依据的那个指纹做比对，因此只有它知道这个文件是否仍然描述着当前生效的规则和配置。如果该文件读不出来，则改为重新扫描该样本。

正是这一点让被中断的运行不会重复它已经做完的那些批次。改动规则本身就会让缓存失效：`rules_dir` 是一个指名目录的配置值，因此规则文件本身会被折进指纹里，而在另一个指纹下记录的结果算作已过期，不会被采纳。对于指纹看不到的那些改动，`deepzero run --redo <stage>` 仍然是强制重新扫描的办法；它之所以有效，是因为凡是写出 `findings.json` 的路径 (包括过滤掉样本的那条路径) 都把它记录为产物，`--redo` 因而能找到并删除这个文件。在指纹机制存在之前记录下来的结果带着一个空摘要，这些结果会被原样信任：仅仅因为一个语料库早于该特性就把它丢弃，是更糟的一种猜测。

被采纳的结果只带有 `finding_count` 和 `findings_cached`。`files_submitted` 和 `files_scanned` 来自 semgrep 运行本身，因此本次并未被扫描的样本这两项都没有。

#### 分批，以及值得知道的几种失败

样本是分批扫描的，而不是一次性扫完，这样某一批超时或返回无法读取的结果时，只会赔上它自己那些样本，而不是在工作已经做完之后丢弃整个语料库的结果。超出 `timeout` 的那一批，会把其中每个样本都记录为失败。

`extensions` 必须与规则保持一致。扩展名未被列出的文件永远不会被交给 semgrep，无论有多少条规则本可以匹配它，而且这种失效是无声的：扫描报告零发现，这与一棵干净的代码树无法区分。这正是源代码审计流水线要在 `finding_count` 之外一并记录 `files_scanned` 的原因。

另有两种结果会被拒绝，而不是被当作干净结果报告出来，因为从外面看它们都与一个干净的语料库一模一样：semgrep 带着加载错误返回且完全没有任何结果，以及 semgrep 列出的已扫描文件里一个提交给它的文件都没有。两者都会让该批次失败并说明原因。

`target_dir` 不在磁盘上的样本会单独失败，而且是在任何批次被组装起来之前，其错误信息会问一句：产出那个目录的阶段是否排在本阶段之前，而这通常正是答案所在。

`min_findings` 是在本阶段过滤掉样本，而不是让它失败，因此它带着一条被记录下来的原因离开本次运行，其 `findings.json` 也依然附在身上。两条内置流水线都设置了 `min_findings: 1`，正是这一点让一个什么都没被标记出来的样本不必在下游白白花掉一次模型调用。
