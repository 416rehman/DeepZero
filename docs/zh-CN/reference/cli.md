## 命令行界面

`deepzero` CLI 是执行和管理流水线的主要交互入口。

```bash
# 标准执行
deepzero run ./targets -p pipelines/loldrivers/pipeline.yaml

# 在投入一次长时间运行之前，先检查 LLM 后端是否已登录
deepzero run ./targets -p pipelines/source_audit/pipeline.yaml --preflight

# 携带状态清理功能执行 (全新运行)
deepzero run ./targets -p pipelines/loldrivers/pipeline.yaml --clean

# 列出磁盘上的每一次运行，无论它由什么产出
deepzero runs

# 生成一份可浏览的 HTML 报告并打开它
deepzero report -p loldrivers --open

# 检查执行状态
deepzero status -p loldrivers

# 启动交互式分析 REPL
deepzero interactive -w work/loldrivers

# 启动 Starlette REST API
deepzero serve -w work/loldrivers --port 8420

# 搭建新的自定义流水线
deepzero init my_custom_pipeline

# 仅验证架构 (不执行)
deepzero validate loldrivers

# 检查系统注册表
deepzero list-processors
```

`deepzero --version` 会打印已安装的版本号，`--help` 对命令组和每一条命令都可用。

### 核心命令

| 命令 | 描述 |
| --------- | ----------- |
| `run` | 针对目标执行流水线。如果状态存在则自动恢复。 |
| `report` | 依据一次运行的结果生成可浏览的 HTML 报告。运行过程中执行也是安全的。 |
| `runs` | 列出磁盘上的每一次运行，无论它由哪条流水线或哪个语料库产出。 |
| `status` | 显示当前流水线运行状态、裁决和阶段指标。 |
| `validate` | 对流水线的架构、处理器导入和提示词进行预运行验证 (Dry-run)。 |
| `list-processors` | 列出所有内置以及动态注册的处理器类型。 |
| `init` | 搭建一个新的流水线目录，并生成标准的 `pipeline.yaml` 样板文件。 |
| `interactive` | 提供由 LLM 支持的、针对流水线结果进行对话的交互式分析 REPL。 |
| `serve` | 启动 REST API 服务器以向外部暴露流水线状态。 |

### `run`

```bash
deepzero run <TARGET> -p <pipeline> [options]
```

| 标志 | 默认值 | 描述 |
|------|---------|-------------|
| `TARGET` | 必须 | 位置参数。分析语料库的路径。必须已存在；可以是文件也可以是目录，取决于流水线的摄取阶段接受哪一种。 |
| `-p, --pipeline` | 必须 | 流水线名称、目录，或离散的 YAML 文件路径。 |
| `-m, --model` | 流水线的 `model` | 本次运行覆盖使用的 LLM 模型，例如 `openai/gpt-4o`。 |
| `-w, --work-dir` | 流水线的 `work_dir` 设置 | 替换构建运行目录时所用的根目录。 |
| `--clean` | 关闭 | 永久删除以往的运行数据并全新开始。 |
| `--preflight` | 关闭 | 运行前先验证 LLM 后端已通过认证。会发起一次极小的调用。 |
| `--redo` | 无 | 重新运行指定的阶段以及它之后的一切，保留更早的工作成果，并删除那些阶段记录过的输出。可重复指定。 |
| `--retry-timeouts` | 关闭 | 重新尝试那些耗尽了时间的样本，同时保留其他所有结果。 |
| `--timeout-multiplier` | `2.0` | 重试某个耗尽时间的阶段时，允许其时长放宽的倍数。 |
| `-v, --verbose` | 关闭 | 详细日志，包含 DeepZero 自身代码的调用栈。 |

没有既有状态的运行会从头开始；有状态的则会恢复，并在标题中说明它接续的是哪一次运行。允许在两次运行之间修改 `--model`，并且这一改动会被记录下来：运行状态会更新为实际将被调用的模型，这样 `status` 和报告就不会去描述一个已经不再使用的模型。

`--clean` 会先把上一个目录改名挪开，再在后台删除它，因此一个包含几十万文件的语料库不会让命令一直卡在删除上。

#### 一次运行的状态存放在哪里

工作目录按语料库划分作用域：

```text
<work_dir setting>/<pipeline name>/<corpus key>/
```

语料库键由目标路径派生而来：它的基本名，加上解析后绝对路径的一段短摘要。因此，经由同一条流水线处理的两个语料库绝不会共用样本存储、清单或报告，各自独立恢复。同一路径始终产生同一个键，所以重新运行会回到它离开时的那个目录。

`run` 上的 `-w, --work-dir` 只替换第一段。流水线段和语料库段仍会被追加上去，因为正是它们把两次运行区分开来。

#### 运行过程中持续生成的报告

一次运行会把它的 HTML 报告写入 `<work dir>/report`，并在第一个阶段开始前打印出 URL。报告是在结果产生时重建的，而不是按定时器重建，并且间隔不短于 15 秒，这样一个快速阶段就不会把运行的时间花在写 HTML 上。运行停止时会再写一次，无论是被中断还是正常结束，因此磁盘上的内容始终是最终状态。

#### 在长时间运行之前检查 LLM

`--preflight` 会询问后端是否已就绪，若未就绪则拒绝启动。它的存在是因为另一种情况是：跑了好几个小时之后，在第一个评估阶段才发现问题，而此前那些昂贵的阶段已经白跑了。

这项检查具体做什么取决于后端，因为“已通过认证”对不同后端意味着不同的事情。像 `claude-code` 这样的 agent CLI 后端会发送一条极小的提示词，因为那个可执行文件是否已登录，DeepZero 无法从磁盘上读出来。基于 API 密钥的后端则直接依据验证阶段已经做过的密钥检查作答，不产生任何开销。

速率限制或网络错误不会被当作认证失败，也不会阻止运行。这项检查是可选启用而非始终开启的，因为那一次提示词哪怕再小，也是真实的用量。

只有当流水线配置了模型时它才会运行。没有 LLM 阶段的流水线无需检查。

#### 重试那些耗尽了时间的样本

一个触及自身 `timeout` 的阶段，会把该样本记录为耗尽了时间，而不是记录为失败。这是关于预算的陈述，而不是关于样本的：触及超时的往往是最大的那些样本，而在多数语料库中它们恰恰最值得一看，把它们和真正的错误归在一起，会悄悄让整次运行偏离它们。

这个预算约束的是阶段等多久，而不是这份工作要跑多久。处理器的线程是被撇下，而不是被杀掉，因此在阶段已经往下走之后，它启动的外部进程仍然在跑。参阅 [`timeout`]({{ '/zh-CN/reference/pipeline-yaml.html' | relative_url }})。

恢复运行不会自动重试它们，因为当初不够用的预算现在依然不够。你需要主动要求：

```bash
deepzero run <target> -p <pipeline> --retry-timeouts
```

这只会遗忘那些耗尽了时间的阶段，并给它们 `--timeout-multiplier` (默认 2 倍) 的时长。运行产出的其他结果一律保留，所以一次重试只花费那些阶段所需的时间，别无其他。未声明超时的阶段不受影响。报告会把它们单独归组，并显示各自超出的预算。

#### 重新运行某一个阶段

改动一份提示词、一套规则或一个扫描器的配置，会让那个阶段的结果失效，而它之前的一切并不受影响。为了重新向语料库提一个问题就把它整个重新反编译一遍，会白白花上几个小时，所以改为指名那个阶段：

```bash
deepzero run <target> -p <pipeline> --redo assess
```

每个样本都会遗忘该阶段以及之后的每一个阶段，并保留更早的一切。之后的阶段也一并遗忘，是因为它们消费的正是即将改变的输出：一份依据已经不复存在的发现写成的评估，会让同一个样本描述两次不同的运行。被某个已作废的阶段过滤掉的样本会重新加入本次运行，因此收窄后的规则集可以对它得出不同的裁决。

那些阶段记录过的输出会跟着状态一起被清掉。有几个处理器把自己在磁盘上的文件当作缓存，直接采纳它而不是重做一遍，所以只遗忘状态会让该阶段重新采纳那份陈旧文件并把它记录为新鲜产物，这比不重做还要糟。因此 `--redo` 会删除被丢弃的那些阶段所记录的每一个产物，并说明它移除了多少个文件。记录在样本自身目录之外的产物会被放过，因为它不归本次运行处置。

`--redo` 可以重复指定，并从其中最靠前的那个阶段开始。未知的阶段名会被拒绝，并列出这条流水线实际拥有的阶段名，而不是被当作无事可做。如果没有任何样本到达过所指定的那些阶段，它会明说，并且什么都不改。

### `report`

```bash
deepzero report -p <pipeline> [--open]
deepzero report -w work/loldrivers/drivers-1a2b3c4d
```

| 标志 | 默认值 | 描述 |
|------|---------|-------------|
| `-p, --pipeline` | 无 | 流水线名称或路径。解析到该流水线最近的一个语料库。 |
| `-w, --work-dir` | 无 | 一个运行目录，也可以是某条流水线的根目录，此时会读取其最近的一个语料库并说明是哪一个。优先级高于 `--pipeline`。 |
| `-o, --out` | `<work_dir>/report` | 报告的写入位置。 |
| `--open` | 关闭 | 生成完成后在浏览器中打开报告。 |
| `-v, --verbose` | 关闭 | 详细日志。 |

两个标志都不是必须的。两个都给出时，由 `--work-dir` 说了算。两个都不给时，`report` 会在 `work` 下搜索，那是字面上叫这个名字的目录，而不是流水线的 `work_dir` 设置。它下面只有一次运行时就直接采用，并说明是哪一次。有多次时会列成一张带编号的表格，而且在终端里它会按编号询问你要哪一次。若调用方根本无处读取答案，则会看到同一份列表，以及那条能精确指名某一次运行的 `deepzero report -w <run>` 命令行，然后以 1 退出，因为在脚本里发起询问会把它挂住。一次运行都没有时它会明说，并以 1 退出。

报告从运行状态派生而来，删掉报告目录再执行一次命令就能把它拿回来。唯一拿不回来的是 `report/marks.json`：它保存着读者标记为已核查的内容，也是那个目录下唯一没有任何阶段能够产出的东西。在运行过程中生成也是安全的：它读取状态文件，且不写入任何运行器所依赖的东西，所以它描述的是生成那一刻的运行状况。

它会写出：

| 文件 | 内容 |
|------|------|
| `index.html` | 摘要和一份有排序的列表，长度有上限 |
| `items/<id>.html` | 每个值得一读的样本各一页，并链接到该样本的产物 |
| `inventory.csv` | 每个样本一行，便于用电子表格查看 |
| `findings.jsonl` | 每条发现一行，每行一个 JSON 对象 |
| `report.json` | 供机器读取的摘要合计值，以及称呼它们所用的那套词汇 |

当一个样本身上有值得读的内容时，它才会获得独立页面：发现、评估、错误，或者某个耗尽了时间的阶段。其余样本仍然在 CSV 里，索引页会说明某个列表在何处被截断，以及剩余部分在哪里。

按流水线名称解析会选取最近的一个语料库；当该流水线见过不止一个语料库时会明确说明，并列出其他几个。最新的那次运行未必就是你要问的那次，而悄悄回答另一个语料库的情况才是最值得避免的失败。用 `--work-dir` 可以精确指定一个。

流水线如何称呼它的样本、它的裁决以及它所指向的对象，都来自流水线的 `report:` 块，而该块位于流水线定义中，不在运行目录里。`--work-dir` 依然能拿到它：运行会记录自己是由哪条流水线写出的，因此该块可以按名称找回来。不过一次运行可能比造出它的那条流水线活得更久，当那条流水线已经加载不出来时，报告会回落到默认词汇，而不是拒绝生成。参阅 [报告块]({{ '/zh-CN/reference/pipeline-yaml.html' | relative_url }})。

### `runs`

```bash
deepzero runs
deepzero runs -w work --open
```

| 标志 | 默认值 | 描述 |
|------|---------|-------------|
| `-w, --work-dir` | `work` | 要搜索的根目录。它下面任意深度处，凡是存有 `run.json` 的目录都算作一次运行。 |
| `--open` | 关闭 | 生成最近那次运行的报告并在浏览器中打开。 |
| `-v, --verbose` | 关闭 | 详细日志。 |

打印出磁盘上每一次运行的表格，无论它由哪条流水线或哪个语料库产出，按从新到旧排列：写出它的那条流水线、语料库目录、这次运行的状态、摄取发现了多少个样本、报告是否已经生成，以及状态最后一次被写入的时间。随后它会打印出 `deepzero report -w <最近的那次运行> --open` 命令行，这样不必把路径敲出来就能打开表格最上面那次运行。

它搜索的是 `run.json` 这个标记文件，位于任意深度，而不是 `<work dir>/<pipeline>/<corpus>/` 这个形状。一次运行确实总是落在那个形状里，但只是相对它自己的那个根目录而言，而 `run` 上的 `-w` 可以把那个根放到任何地方：从这里按形状去匹配，会漏掉每一次其根目录不是当前被搜索的那个根的运行。

报告那一列写的是 `built` 或 `not built`。这是关于目录的事实，而不是关于结果的事实：报告由运行状态派生而来，因此 `not built` 意味着只差一条命令，而不是丢了。

当根目录不是一个目录时它以 1 退出，当它确实是目录但其中没有任何运行时也以 1 退出。

### `status`

```bash
deepzero status -p loldrivers
```

| 标志 | 默认值 | 描述 |
|------|---------|-------------|
| `-p, --pipeline` | 无 | 流水线名称或路径。解析到该流水线最近的一个语料库。 |
| `-w, --work-dir` | 无 | 一个运行目录，也可以是某条流水线的根目录，此时会读取其最近的一个语料库并说明是哪一个。优先级高于 `--pipeline`。 |
| `-v, --verbose` | 关闭 | 详细日志。 |

两者必须提供其一。会打印运行 id、目标、模型、时间戳、一张按阶段列出已完成、已过滤、已失败和耗尽了时间这几项计数的表格，以及样本裁决的合计。耗尽了时间单独占一列，这样一个所有样本都超时的阶段，才不会读起来像是一个没有任何样本到达过的阶段，而后者与实际情况恰好相反。

### `validate`

```bash
deepzero validate <PIPELINE_REF>
```

加载流水线，解析每一个处理器，运行各处理器自己的 `validate()`，并依据其之前各阶段实际产出的值来检查每一份提示词。它不接受任何标志。请在长时间运行之前执行它：这是发现缺失的二进制文件、无法读取的规则集，或提示词引用了任何阶段都不记录的名称的最廉价场所。

报告出错误时它以 1 退出，否则以 0 退出，因此可以用它来把关一次提交。警告 (例如某条流水线没有配置模型) 只会被打印出来，不会让命令失败：它们描述的是一条能启动起来的流水线，而不是一条启动不了的。

### `list-processors`

打印每一个已注册的处理器及其类型和实现类。不接受任何标志。只列出内置处理器；外部处理器是在加载时按路径解析的，并不会以某个名称注册。

### `init`

```bash
deepzero init <NAME>
```

在工作目录下创建 `pipelines/<NAME>/pipeline.yaml`，内含带注释的骨架。若目录已存在，它会拒绝执行而不是覆盖。

### `interactive`

```bash
deepzero interactive -w work/loldrivers/drivers-1a2b3c4d
```

| 标志 | 默认值 | 描述 |
|------|---------|-------------|
| `-m, --model` | `claude-code/claude-opus-5` | 用于对话的模型。任何后端接受的模型字符串均可。 |
| `-w, --work-dir` | `work` | 从中加载上下文的运行目录。 |
| `-v, --verbose` | 关闭 | 详细日志。 |

这是一个 REPL，它把一次运行的状态载入系统提示词，以便就此提问。`/status`、`/findings [filter]`、`/clear`、`/help` 和 `/quit` 在本地处理；其余内容都会发送给模型，而无法识别的 `/word` 会被指出来，不会被当作一次对话轮次计费。`/findings` 会列出本次运行记录的每一条发现，只保留与其参数匹配的那些行，并采用写出这次运行的那条流水线所声明的词汇。

`-w` 接受一个运行目录，也接受某条流水线的根目录，当其下不止一个语料库时会说明它选中了哪一个。它的默认值就是字面上的 `work`，那是位于各流水线目录之上的根目录，解析下来对应不到任何一次运行；此时 REPL 会明说这一点，并在没有运行上下文的情况下作答，而不是假装已经加载了某次运行，所以请用 `-w` 指向你真正想要的那次运行。

`report` 在一个光秃秃的 `work` 下确实能找到一次运行，而这里却不行，这是一处真实的差别，而不是其中某一边写错了：`report` 会在整棵树里搜索运行目录，而 `interactive` 只解析一层，并在拿到的那个目录下取最近的一个语料库。一次对话值得用“被要求指名那次运行”换来的确定性；而一份报告，换一次运行重新生成也很廉价。

### `serve` 与 REST API

| 标志 | 默认值 | 描述 |
|------|---------|-------------|
| `--host` | `127.0.0.1` | 绑定主机。非回环地址会打印一条警告，因为此时服务器可从网络访问。 |
| `--port` | `8420` | 绑定端口。 |
| `-w, --work-dir` | `work` | 要提供服务的工作目录。可以是一个运行目录，也可以是某条流水线的根目录，此时会提供其最近的一个语料库并说明是哪一个。 |

需要额外依赖：`pip install deepzero[serve]`，它会一并装上 Starlette 和 uvicorn。

> [!WARNING]
> **开发中 / 实验性功能**
> REST API 服务器目前尚未完成，极不稳定，**不应被使用**。提供它仅用于实验性的本地开发。

启动一个只读的 Starlette REST API 以供查询运行状态和样本数据。它只服务于一次运行，这也正是工作目录要在打印 URL 之前就解析到单个语料库、而不是等到某个请求返回空结果之后才解析的原因。

| 终端节点 | 方法 | 描述 |
|----------|--------|-------------|
| `/api/health` | GET | 健康检查，并给出正在服务的工作目录 |
| `/api/runs` | GET | 以单元素列表返回所服务的那次运行，没有则返回空列表 |
| `/api/run` | GET | 该次运行的完整状态，没有则返回 404 |
| `/api/samples` | GET | 列出样本 (可通过 `?verdict=`, `?classification=`, `?stage=`, `?status=` 进行过滤) |
| `/api/samples/{sample_id}` | GET | 获取包含历史流水线数据的完整样本状态 |
| `/api/samples/{sample_id}/artifacts/{name}` | GET | 读取由某个处理器生成的特定文件产物 |

`verdict` 是样本从流水线中离开的位置，`classification` 则是某个阶段对它得出的结论。两者都会随响应一起返回，因此各自筛选的正是与其同名的那个字段。`stage` 匹配的是样本当前所在的阶段；`status` 会在样本历史中任何一个阶段带有该状态时保留该样本。含有路径分隔符的样本 id 会被拒绝，因为这个 id 会变成一个文件系统路径，而这个服务器是可以被绑定到所有网络接口上的。
